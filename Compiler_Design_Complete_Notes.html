1.1 Compilers and Translators

What is a Translator?

A translator is a program that takes a program written in one language (the source language) and converts it into an equivalent program in another language (the target language). During this process, it also reports errors in the source program.

📖 Definition — Compiler
A compiler is a translator that reads a program written in a high-level language (source language) and translates it into an equivalent program in machine language or assembly language (target language). The entire source program is translated before execution begins.

Types of Translators

Need of Translators

  1. Bridge the Gap: Humans think in high-level constructs; machines understand only binary.
  2. Portability: Programs written in high-level languages can run on different machines.
  3. Optimization: Compilers can optimize code for better performance.
  4. Error Detection: Translators catch syntax errors, type mismatches, and semantic errors.
  5. Abstraction: Programmers can focus on problem-solving without worrying about hardware.

1.2 Structure of a Compiler — Phases

A compiler operates in a sequence of phases, each of which transforms the source program from one representation to another. The phases can be grouped into the front end (analysis) and the back end (synthesis).

Phase 1: Lexical Analysis (Scanner)

Reads the source program character by character and groups them into meaningful sequences called lexemes. For each lexeme, it produces a token: <token-name, attribute-value>.

✅ Example

Input: position = initial + rate * 60

Output tokens:

<id, 1>  <=, >  <id, 2>  <+, >  <id, 3>  <*, >  <num, 60>

Where id 1 → position, id 2 → initial, id 3 → rate (stored in symbol table)

Phase 2: Syntax Analysis (Parser)

Takes the token stream and creates a parse tree (syntax tree) that represents the grammatical structure.

✅ Syntax Tree for position = initial + rate * 60
          =
         / \
       id1   +
            / \
          id2   *
               / \
             id3  60

Phase 3: Semantic Analysis

Checks for semantic consistency — type checking, scope resolution, type coercion (e.g., integer 60 → float 60.0).

Phase 4: Intermediate Code Generation

Generates a machine-independent intermediate representation (IR). Common form: three-address code.

✅ Three-Address Code
t1 = inttofloat(60)
t2 = id3 * t1
t3 = id2 + t2
id1 = t3

Phase 5: Code Optimization

Improves intermediate code for speed/memory without changing meaning.

✅ Optimized
t1 = id3 * 60.0
id1 = id2 + t1

Phase 6: Code Generation

Translates optimized IR into target machine code.

✅ Assembly Output
LDF  R2, id3
MULF R2, R2, #60.0
LDF  R1, id2
ADDF R1, R1, R2
STF  id1, R1

Cross-cutting Components

ComponentRole
Symbol Table ManagerMaintains identifiers with their attributes (type, scope, memory). Used by all phases.
Error HandlerDetects, reports, and recovers from errors in each phase.

1.5 Input Buffering

Reading one character at a time from disk is slow. Input buffering reads large blocks into memory.

Two pointers:

  • lexemeBegin — points to the beginning of the current lexeme
  • forward — scans ahead until a pattern match is found
⚡ Sentinel Scheme
Without sentinel: 2 tests per character (end-of-buffer + character). With sentinel (eof at end of each half): only 1 test per character.

1.7 Finite Automata (DFA and NFA)

📖 NFA — Non-deterministic Finite Automaton
M = (Q, Σ, δ, q₀, F) where δ: Q × (Σ ∪ {ε}) → 2Q. Allows multiple transitions on same symbol and ε-transitions.
📖 DFA — Deterministic Finite Automaton
Special case of NFA: no ε-transitions, exactly one next state for each state and input. δ: Q × Σ → Q.
FeatureNFADFA
ε-transitionsAllowedNot allowed
Multiple transitions on same inputAllowedNot allowed
Number of statesFewerCan be 2ⁿ (exponential)
Simulation speedSlower (backtracking)O(n) for string length n
Construction from REEasier (Thompson's)Harder (subset construction)

Subset Construction: NFA → DFA

Key Operations
OperationDescription
ε-closure(s)Set of states reachable from s via ε-transitions only
ε-closure(T)Union of ε-closure(s) for all s in set T
move(T, a)Set of states reachable from T on input 'a'
 
Algorithm: Subset Construction (NFA → DFA)
1. d₀ = ε-closure(q₀)              // DFA start state
2. Add d₀ to Q_D (unmarked)
3. while (unmarked state T in Q_D):
     mark T
     for each a ∈ Σ:
       U = ε-closure(move(T, a))
       if U ∉ Q_D: add U (unmarked)
       δ_D(T, a) = U
4. F_D = {T ∈ Q_D | T ∩ F_N ≠ ∅}

1.9 Minimizing Number of States of DFA

📖 Equivalent States
States p and q are equivalent if for every string w: δ(p,w) ∈ F ⟺ δ(q,w) ∈ F.

Hopcroft's Algorithm (Partition Refinement)

1. Initial Partition: Π = { F, Q - F }
2. Repeat:
     For each group G in Π:
       Split G into subgroups where states s,t are
       together iff for ALL inputs a, δ(s,a) and δ(t,a)
       fall in the SAME group.
3. Until no more splits (Π converges)
4. Each group = one state in minimized DFA

Structure of a LEX Program

%}

/* Definitions */

// Simplified hand-coded lexical analyzer
Token getNextToken() {
    char c;
    while ((c = getchar()) == ' ' || c == '\t' || c == '\n');
    
    if (isalpha(c)) {        // Identifiers & keywords
        char buf[100]; int i = 0;
        buf[i++] = c;
        while (isalnum(c = getchar())) buf[i++] = c;
        buf[i] = '\0';
        ungetc(c, stdin);
        if (strcmp(buf, "if") == 0) return TOKEN_IF;
        if (strcmp(buf, "while") == 0) return TOKEN_WHILE;
        return TOKEN_ID;
    }
    if (isdigit(c)) {        // Numbers
        int val = 0;
        do { val = val*10 + (c-'0'); } while (isdigit(c = getchar()));
        ungetc(c, stdin);
        return TOKEN_NUM;
    }
    switch (c) {             // Operators
        case '+': return TOKEN_PLUS;
        case '*': return TOKEN_STAR;
        case '<':
            c = getchar();
            if (c == '=') return TOKEN_LE;
            ungetc(c, stdin);
            return TOKEN_LT;
    }
}

Syntax Analysis (Parsing) — The Second Phase of Compilation

2.1 Role of the Parser

The parser receives tokens from the lexical analyzer and checks whether the token sequence conforms to the language grammar. It constructs a parse tree.

Types of Parsers

🔽 Top-Down Parsers

Root → Leaves. Leftmost derivation.

  • Recursive Descent
  • Predictive (LL(1))
🔼 Bottom-Up Parsers

Leaves → Root. Rightmost derivation in reverse.

  • Shift-Reduce
  • Operator Precedence
  • LR (SLR, LALR, CLR)

Error Recovery Strategies

StrategyDescription
Panic ModeSkip tokens until a synchronizing token (;, }) is found
Phrase LevelLocal correction — insert/delete tokens
Error ProductionsAdd grammar rules for common errors
Global CorrectionMinimum-cost edit (theoretical)

2.2 Context-Free Grammars (CFG)

📖 Context-Free Grammar
G = (V, T, P, S) where:
  • V — non-terminals (E, T, F, S)
  • T — terminals (id, +, *, (, ))
  • P — productions: A → α
  • S — start symbol
✅ Grammar for Arithmetic Expressions
E → E + T | T
T → T * F | F
F → ( E ) | id

Leftmost Derivation of id + id * id:

E ⇒ E+T ⇒ T+T ⇒ F+T ⇒ id+T ⇒ id+T*F ⇒ id+F*F ⇒ id+id*F ⇒ id+id*id

Rightmost Derivation:

E ⇒ E+T ⇒ E+T*F ⇒ E+T*id ⇒ E+F*id ⇒ E+id*id ⇒ T+id*id ⇒ F+id*id ⇒ id+id*id

2.4 Eliminating Ambiguity

📖 Ambiguous Grammar
A grammar where at least one string has more than one parse tree (or leftmost/rightmost derivation).
🔢 Example — Ambiguous Grammar

Grammar: E → E + E | E * E | ( E ) | id

String: id + id * id has two parse trees:

Tree 1: +(id, *(id,id))     → id + (id*id)   ← correct
Tree 2: *(+(id,id), id)     → (id+id) * id   ← wrong!

Fix: Enforce precedence (* before +) and associativity (left-to-right):

E → E + T | T
T → T * F | F
F → ( E ) | id
🔢 Dangling Else Problem

Ambiguous: stmt → if E then stmt | if E then stmt else stmt | other

Fix (else matches nearest if):

stmt → matched | unmatched
matched → if E then matched else matched | other
unmatched → if E then stmt | if E then matched else unmatched

2.5 Elimination of Left Recursion

📖 Left Recursion
A → Aα | β. Causes infinite loops in top-down parsers.
A → Aα | β   ⟹   A → βA',   A' → αA' | ε
🔢 Solved Numerical — Remove Left Recursion

Original:

E → E + T | T
T → T * F | F
F → ( E ) | id

After removal:

E → T E'
E' → + T E' | ε
T → F T'
T' → * F T' | ε
F → ( E ) | id
🔢 Indirect Left Recursion

Given: S → Aa | b,   A → Sd | ε

S ⇒ Aa ⇒ Sda (indirect: S produces S)

Substitute S into A: A → Aad | bd | ε

Remove: A → bdA' | A',   A' → adA' | ε

2.6 Left Factoring

A → αβ₁ | αβ₂   ⟹   A → αA',   A' → β₁ | β₂
🔢 Solved Example

Given: S → iEtS | iEtSeS | a  (i=if, E=expr, t=then, e=else)

Common prefix: iEtS

After Left Factoring:

S → iEtSS' | a
S' → eS | ε
E → b

2.7 Top-Down Parsing — Recursive Descent

Uses mutually recursive procedures — one per non-terminal.

🔢 Recursive Descent Parser Code

Grammar: E → TE', E' → +TE' | ε, T → FT', T' → *FT' | ε, F → (E) | id

Token lookahead;

void E()       { T(); E_prime(); }
void E_prime() { if (lookahead == '+') { match('+'); T(); E_prime(); } }
void T()       { F(); T_prime(); }
void T_prime() { if (lookahead == '*') { match('*'); F(); T_prime(); } }
void F() {
    if (lookahead == '(') { match('('); E(); match(')'); }
    else if (lookahead == ID) { match(ID); }
    else error("Expected ( or id");
}
void match(Token expected) {
    if (lookahead == expected) lookahead = getNextToken();
    else error("Unexpected token");
}

2.8 Non-Recursive Predictive Parsing & LL(1) Grammars

FIRST and FOLLOW Sets

📖 FIRST(α)
Set of terminals that begin strings derivable from α. If α ⇒* ε, then ε ∈ FIRST(α).
📖 FOLLOW(A)
Set of terminals that can appear immediately right of A. $ ∈ FOLLOW(S).
FIRST Rules
  1. If X is terminal: FIRST(X) = {X}
  2. If X → ε: add ε to FIRST(X)
  3. If X → Y₁Y₂...Yₖ: add FIRST(Y₁)−{ε}; if ε ∈ FIRST(Y₁), add FIRST(Y₂)−{ε}; etc.
FOLLOW Rules
  1. $ ∈ FOLLOW(S)
  2. A → αBβ: add FIRST(β)−{ε} to FOLLOW(B)
  3. A → αB or A → αBβ with ε ∈ FIRST(β): add FOLLOW(A) to FOLLOW(B)
🔢 Solved — FIRST and FOLLOW Sets

Grammar: E→TE', E'→+TE'|ε, T→FT', T'→*FT'|ε, F→(E)|id

For each production A → α:
  For each a ∈ FIRST(α): add A→α to M[A,a]
  If ε ∈ FIRST(α): for each b ∈ FOLLOW(A): add A→α to M[A,b]

2.11 LR Parsing — SLR, LALR, and Canonical LR

LR parsing = Left-to-right scan, Rightmost derivation in reverse. Most powerful deterministic bottom-up technique.

LR(0) Items

📖 LR(0) Item
A production with a dot (•) at some position. For A → XYZ: A→•XYZ, A→X•YZ, A→XY•Z, A→XYZ• 
CLOSURE(I):
  For each A → α•Bβ in I, add all B → •γ to I

GOTO(I, X):
  Move dot past X: {A→αX•β | A→α•Xβ ∈ I}, then CLOSURE
🔢 Solved — SLR Parsing Table Construction

Augmented Grammar:

(0) S' → S
(1) S → AA
(2) A → aA
(3) A → b

Canonical LR(0) Collection:

I₀ = CLOSURE({S'→•S}) = {S'→•S, S→•AA, A→•aA, A→•b}

I₁ = GOTO(I₀,S) = {S'→S•}

I₂ = GOTO(I₀,A) = {S→A•A, A→•aA, A→•b}

I₃ = GOTO(I₀,a) = {A→a•A, A→•aA, A→•b}

I₄ = GOTO(I₀,b) = {A→b•}

I₅ = GOTO(I₂,A) = {S→AA•}

I₆ = GOTO(I₃,A) = {A→aA•}

GOTO(I₂,a) = I₃, GOTO(I₂,b) = I₄, GOTO(I₃,a) = I₃, GOTO(I₃,b) = I₄

FOLLOW: FOLLOW(S) = {$}, FOLLOW(A) = {a, b, $}

📖 LR(1) Item
[A → α•β, a] — LR(0) item + lookahead terminal 'a'. Lookahead used only for complete items (β = ε): reduce only if next input = a.
⚡ LALR vs CLR
LALR merges CLR states with same core (LR(0) items), combining lookaheads. May introduce reduce-reduce conflicts but never shift-reduce. Produces same number of states as SLR.
